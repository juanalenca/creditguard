Slide 6 — Ciência de Dados
Ruan Deud

"A etapa de Ciência de Dados foi uma das mais importantes do projeto, pois foi responsável por transformar dados brutos em informações confiáveis para todo o sistema.

Trabalhamos com dois conjuntos de dados reais fornecidos pela disciplina.

O primeiro foi o arquivo cobranca_assessorias.csv, contendo aproximadamente dez mil contratos financeiros.

O segundo foi o arquivo fluxo_pagamentos.xlsx, contendo cerca de cem mil registros relacionados a pagamentos e movimentações financeiras.

Antes de qualquer análise, foi necessário realizar um processo completo de ETL, ou seja, Extração, Transformação e Carga dos dados.

Utilizando Python e Pandas, realizamos a leitura dos arquivos, tratamento de encoding, padronização textual, correção de inconsistências e remoção de problemas que poderiam comprometer as análises.

Também realizamos a conversão de valores monetários para formatos adequados para cálculo e a normalização de datas utilizando recursos do Pandas.

Outro passo importante foi a integração entre contratos e pagamentos através dos identificadores presentes nas bases.

Esse relacionamento permitiu construir uma visão consolidada da carteira financeira.

Após todas essas transformações, os dados foram carregados no PostgreSQL, tornando-se a base analítica utilizada pelo restante da aplicação."

---

Slide 7 — Regras Heurísticas e Insights
Ruan Deud

"Com os dados já tratados e estruturados, iniciamos a etapa de análise exploratória e construção das regras de negócio.

Foram realizadas análises relacionadas à distribuição regional da inadimplência, comportamento temporal dos pagamentos, concentração financeira por assessoria e identificação de contratos classificados como risco alto.

A partir dessas análises implementamos regras heurísticas para classificação automática de risco.

Os contratos foram classificados automaticamente em três níveis de risco. Contratos com até 15 dias de atraso foram classificados como risco baixo. 
Entre 16 e 60 dias, risco médio. Já os contratos com atraso superior a 60 dias, status ajuizado ou score interno acima de 70 foram classificados como risco alto. 
Essas regras permitiram identificar automaticamente os contratos classificados como risco alto e alimentar o sistema de alertas.

Como resultado das análises, identificamos aproximadamente vinte milhões e seiscentos mil reais em valores inadimplentes monitorados pela plataforma.

Também observamos uma taxa de recuperação próxima de vinte e cinco por cento e identificamos 8.925 contratos classificados como risco alto de acordo com as regras heurísticas definidas para o projeto.

Todos os indicadores, gráficos e insights exibidos posteriormente no dashboard são derivados desse trabalho realizado na camada de Ciência de Dados.

Agora o Matheus apresentará a arquitetura da solução."

Slide 8 — Arquitetura da Solução
Matheus Henrique

"A arquitetura da aplicação foi construída de forma modular, separando claramente as responsabilidades de cada componente.

O fluxo inicia nos datasets financeiros processados pela camada de Ciência de Dados.

Após o tratamento realizado em Python e Pandas, os dados são armazenados no PostgreSQL, que atua como repositório central da aplicação.

O backend desenvolvido em Node.js e Express realiza consultas analíticas sobre essa base e disponibiliza os resultados por meio de APIs REST.

O frontend React consome essas APIs e apresenta os resultados aos usuários através dos dashboards.

Essa arquitetura facilita manutenção, escalabilidade e reutilização dos componentes.

Além disso, toda a estrutura foi projetada para garantir que os indicadores gerados pela Ciência de Dados estejam disponíveis de forma consistente para os usuários finais."

---

Slide 9 — Backend e Banco de Dados
Allan

"No backend utilizamos Node.js e Express para construção das APIs responsáveis pela comunicação entre banco de dados e interface.

O PostgreSQL foi utilizado como banco principal, armazenando contratos, pagamentos, usuários e alertas de risco. Utilizamos o PostgreSQL hospedado no Supabase, o que permitiu disponibilizar o banco em nuvem sem a necessidade de manter uma instância local em execução durante o desenvolvimento e os testes.

As consultas implementadas utilizam operações SQL como SUM, COUNT, AVG e GROUP BY para gerar indicadores financeiros de forma eficiente.

Essa estratégia evita que grandes volumes de dados precisem ser processados diretamente no navegador.

Os resultados dessas consultas são disponibilizados por endpoints específicos responsáveis pelos KPIs, alertas e insights.

É importante destacar que esses indicadores são calculados sobre os dados previamente tratados pela camada de Ciência de Dados, garantindo consistência e confiabilidade das informações apresentadas."

Slide 10 — Dashboard Executivo
João Guilherme

"O frontend foi desenvolvido utilizando React e Vite, adotando o conceito de Single Page Application.

O dashboard apresenta os KPIs definidos nos requisitos do projeto, incluindo inadimplência total, recuperação financeira, atraso médio, risco regional e tendência temporal.

Slide 12 — Segurança e Governança
Victor

Do ponto de vista da governança, adotamos mecanismos voltados para integridade, consistência e padronização dos dados.
